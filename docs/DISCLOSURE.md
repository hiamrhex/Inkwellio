# Disclosure

What an outsider can learn from a browser and from a request, what this repository removes, what it
cannot, and which test fails if a control is reverted.

Read this with [A13](./design-amendments.md) (browser posture) and [ADR-015](./adr/015-slug-case-and-encoding.md).
The premise is uncomfortable and worth stating: hiding the framework is obscurity, not security. Anyone can
see `/_next/` assets and read the page structure. The controls below therefore aim at three things that
actually matter — no known-vulnerable version, no server-side detail in a response, and nothing secret in
the client bundle — and the table says plainly what still leaks.

Every "control" below has a test. A control without a failing test is a wish.

## The table

## Things that cannot be hidden, stated once

- **The framework.** `/_next/static/...` URLs, the RSC payload embedded in the HTML, and the shape of the
  markup all identify Next.js. `poweredByHeader: false` removes a banner, not the fact.
- **The hosting platform.** Its headers arrive before any application code runs. On Vercel expect `server`,
  `x-vercel-cache`, `x-vercel-id`, and `x-matched-path` on some responses.
- **The build.** `/_next/static/<buildId>/` is a per-deploy identifier. It is how assets are versioned; it
  cannot be removed without breaking caching.
- **That an error occurred.** A digest on an error page confirms a server error. That is the intended
  trade: a user can quote one identifier, and the server log can be searched for it, without the user
  learning what failed.

## What is deliberately not attempted

- Renaming framework asset prefixes, the auth base path, or the session cookie to look less like a known
  stack. It breaks defaults, breaks clients, and buys nothing against an attacker who reads HTML.
- A WAF, bot detection, or header obfuscation. Those are A12/WP8 questions, not disclosure controls.

## How to re-check

1. `pnpm check` — runs every test above in CI.
2. `curl -sI https://<deployment>/` once deployed, compare against row 9 and record it in EVIDENCE (U-11).
3. On any dependency upgrade, re-read <https://nextjs.org/blog/security> and record the date, per row 13.
